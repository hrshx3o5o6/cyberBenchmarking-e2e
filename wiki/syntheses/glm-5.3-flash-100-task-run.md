# GLM 5.3 Flash on the same 100 tasks, setup A: setup record and observations (living, started 2026-11-09)

The DeepSeek V4.1 Flash run ([[wiki/syntheses/deepseek-100-task-run-report]], rerun record in its section 19) repeated with GLM 5.3 Flash through OpenRouter (provider pinned to Z.AI, [[wiki/syntheses/glm-5.3-flash-openrouter-setup]]) and graded with setup A ([[wiki/syntheses/grader-shared-images-experiment]]). Everything below is what was set up and what was observed, in time order; times are UTC.

## 4. The run collapsed at 19:35 UTC: one runaway agent container exhausted the head's memory (post-mortem, 2026-11-10)
**Outcome.** Of the 100 tasks only **12 finished** (1 passed all four stages, `opensc/arvo_20131`, 15 minutes, $0.19; 3 passed S1 to S3 and failed S4; 2 failed S1; 6 hit the 90-minute limit with no patch); **88 ended as `infra_error` without a model result** (76 never started, 8 on the workers, 4 on the head). The driver exited at 20:02:14 with `EXIT=1`. Setup A graded the three tasks that reached grading (`validation_mode: shared`, no leftover image); nothing in the failure involves grading.

**Timeline** (head sampler in Postgres `node_metrics`, driver log, console log):

| 19:27 | `mruby/arvo_65996` starts on the head (execution `41c9b934...`; 54 model calls, $0.11 before the failure) |
| 19:32:02 | head memory in use 9.9 GB; container `codex-caf72ea5` (the mruby agent container, inferred from the process name `mruby_fuzzer`) still at 0.1 GB |

| 04:47 | reboot from the console; the head came back by itself at 04:52 (Postgres healthy, disk 141 GB free) |

**What is established:** (1) a single agent container grew from 0.1 GB to about 50 GB in under three minutes, five minutes after its task started; (2) the head ran the Ray memory monitor and Postgres and the driver, so one task on the head took the control plane with it; (3) the harness sets no memory or process limit on a container, and does not clean up an agent container whose task process was killed; (4) the flood was `mruby_fuzzer` instances (ASan binaries, 355 MB each, hundreds at once).
**What is not:** the command that started the fuzzers. The agent's trajectory is written to disk only at the end of a task, so the files of this task are empty and the container died with the reboot; the shim log holds no commands. It was probably the agent running the fuzzer in parallel (fuzzer workers or a background loop), not the task's own scripts (they replay one input once), but that is an inference. **Why this did not happen in the DeepSeek run:** unknown. The same task list ran there with a peak of 34 GB per node; possible reasons are that DeepSeek did not start parallel fuzzers on these tasks, or that such a task landed on a worker (where it would only have harmed that worker). The DeepSeek first pass did lose two workers to out-of-memory with ten slots per node.

**Cost.** OpenRouter spend about $45 (the head's shim logged $15.93 over 3,370 calls; finished tasks account for $31.81 of it; the workers' shim logs are gone with the instances). No model calls happened after about 19:35 (the head's shim log ends there), so the orphaned container did not run up spend; only the OpenRouter dashboard figure is authoritative.
**What was lost.** Worker disks went with the terminated workers; the results and artifacts that were synced to Postgres remain (12 finished rows). The head's own files, the shim log and the memory sampler (`node_metrics`) survive.

**Setup A is not implicated:** the culprit is an agent container (`codex-...`, 5 minutes into its task, before any grading), not a validation container, and the head allows only two shared validations at once.

## 5. Run 2: all 100 tasks again, with container limits (launched 2026-11-10 06:20:49 UTC)
**Changes made after the collapse of run 1** (all optional switches in the nodes' `config/.env`, each patch with a backup and an undo, delivered to workers through the cluster template):
| Change | Setting | Where |
|---|---|---|
| **memory and process limit on every container, agent and validation** | 40 GB (`--memory` and `--memory-swap`, so no swap) and 2,048 processes | `tools/patch_container_limits.py` on the harness `utils.py` (`CYBERGYM_CONTAINER_MEM_GB=40`, `CYBERGYM_CONTAINER_PIDS=2048`); `cleanup_container` logs `CONTAINER_OOM: <id> oom_kill=<n>` when the kernel killed something in a container |
| **janitor** for orphaned agent containers | stops any `codex-*` container running longer than 120 minutes, every 60 s, on every node | `tools/container_janitor.py` |
| **apt mirror** | `CYBERGYM_APT_MIRROR=us-east-1.ec2.archive.ubuntu.com`: every container's apt sources are rewritten to the AWS regional mirror | `tools/patch_apt_mirror.py` (see below) |
| manifest | all 100 tasks (not only the 88 failed ones), the DeepSeek run's order, new work_root `random100-glm53flash-r2` | `config/random100-glm53flash-r2.json` |
| unchanged | head 4 slots (decided by the study owner), 2 workers of 6, Codex 0.118.0, 90 minutes, 10 USD per run, setup A (head: at most 2 shared validations at once, minimum free disk 120 GB), shim caps 300 USD per node, Z.AI pinned | |
Sizing of the limit: the DeepSeek run's sampler (276 containers, 30-second samples) peaked at 23 GB for the largest agent container (3 above 16 GB, 11 above 8 GB, 21 above 4 GB; no validation container among the 12 largest); the runaway of run 1 reached 60 GB. Tests on the head: unset variables give no limit; a 4 GB allocation against a 2 GB cap was killed (exit 137) while the container, a bystander process and `docker exec` stayed alive and the cleanup logged the kill; a process flood against a cap of 64 was throttled (while saturated even `docker exec` fails until the processes exit, which is why 2,048 is generous). With the study owner's choice the margin on a 61.8 GB node is thin (one container at 40 GB plus the head's own services and three other tasks stays below Ray's 95% threshold of 58.7 GB; two runaways at once could still trip it).

**An external slowdown found and worked around before launch** (2026-11-10 about 05:12 to 06:15): after the reboot every grading check was about five times slower (igraph 650 to 740 s instead of 120 s) and the standard grader returned empty stage results. Not the limits (the same slowness without them), not the reboot, not Docker or DNS: **`archive.ubuntu.com` answered in 17 to 30 s per request from the host and from containers, while the AWS regional mirror `us-east-1.ec2.archive.ubuntu.com` answered in 0.1 s** (host and container; security.ubuntu.com was also slow, 1 to 29 s). Every task's set-up, agent install and grading starts with `apt-get`, so this slows tasks and can make set-up fail silently (the empty stage results). With the mirror variable the harness's own apt step took 5 s (35 s without); the grading check under the real settings (40 GB, 2,048, mirror) gave igraph passed x4 in 117.7 s shared and 145.4 s standard with identical statuses and no image left. The packages come from the same Ubuntu archive; this is part of the setup and goes in the writeup.
