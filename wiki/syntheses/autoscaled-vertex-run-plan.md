# Plan: 100 random tasks, e2e, DeepSeek V4.1 Flash on Vertex, on the Ray autoscaler (no service account yet)

**Status: plan locked 2026-11-03 after a re-check against the files; nothing of it built or run.** Goal: run the sample of [[wiki/syntheses/qwen-100-task-study-protocol]] (same 100 tasks, e2e, same limits and screens; the model is DeepSeek V4.1 Flash on Vertex, so it needs its own protocol variant) across the head and autoscaled workers before a Google service account or federation exists. Background: [[wiki/syntheses/model-registry-design]], [[wiki/syntheses/vm-session-checklist]] (the single-task smoke test that passed, head only), [[wiki/syntheses/vm-stop-and-bring-up-runbook]].

## 1. What has to be solved, and why
| Problem | Why it appears with the autoscaler |
|---|---|
| Google access on workers | workers launch from the image with no credential; a personal login must not be copied to them |
| Wrong shim on workers | the worker start command runs the Bedrock-only script, and **the template syncs only `start_worker_services.sh` from `tools/`** (the rest of `tools/` comes from the baked image, which has the old shim), so new tool files do not reach workers unless added to the file sync |
| Images and task data on workers | section 2 |
| Slots per node | **decision (2026-11-03): stay at 10 per node** (the template's value; head plus 2 workers is 30 slots). The vault's calibration said e2e at 10 on 16 vCPUs is busy but workable (CPU pressure 65 to 80 for about 20 minutes mid-run; grading stretched 1.5 to 5 times under load, on Kimi) and 7 to 8 is the safer figure; stage 6 measures it, and 8 is a one-line fallback |
| Provider limits | Vertex quota for the DeepSeek model is unknown; one e2e run made about 64 model calls a minute at 10 concurrent, so about 150 to 190 a minute at 24 to 30; the shim retries a 429 only 3 times |
| Context window | DeepSeek's limit on Vertex is unknown (earlier Qwen e2e calls reached 172K tokens; the smoke test saw 23K) |
| Runaway launches | a worker whose shim cannot start never joins and the autoscaler may keep launching |
| The Mac | token refresh depends on a laptop staying on, online and logged in |
| vCPU quota | the only proven figure is 48 vCPUs at once (head plus 2 workers) |
| Head disk | Postgres lives on the head's disk; a full disk fails everything |

## 2. How images and task data reach a node (corrected 2026-11-03)
- The harness starts every container with `docker run -d --rm <image> sleep infinity` (`start_container` in the upstream utilities). **`docker run` pulls a missing image by itself**, so a task pulls its own image the first time a node needs it; the pull is outside the agent timer (results report agent time and total duration separately) but inside the task deadline. An earlier statement that the run code never pulls was wrong.
- **Task data** is not fetched by the harness; the runner's `prepare` downloads it. Our template runs `prepare` for the whole manifest on every worker at launch (`cybergym-eval prepare --config ... --skip-firewall`), which also **pulls every image in the manifest**: fine for the light 30-task manifest, but for the random 100 it would try to pull all 67 non-shared images on every worker before it joins.
- **Task data sizes (measured 2026-11-03):** typical tasks 12 to 70 MB (three sample tasks: 12, 25 and 70 MB, downloaded in 14 seconds); a few are huge (two ffmpeg oss-fuzz tasks of about 1.8 GB each); the head's data folder is 7.3 GB for 85 tasks. A worker's setup downloads the manifest's data before it joins, so the time for about 100 tasks is to be measured in the ramp; a file sync of the head's data folder is the alternative if it is slow or Hugging Face rate-limits several workers.
- Fix: workers fetch task data only (a small standalone script, `fetch_task_data.py`, built and tested; the runner needs no change) and images are pulled on demand, paid by the first task on each node. Docker Hub limits anonymous pulls (about 100 per 6 hours per address); a worker pulls a few dozen.
- **Worker disks: 512 GiB gp3, the same as the head** (default 3,000 IOPS and 125 MB/s; each worker has its own volume; about 450 GB free after the system, base images and code). Today's setting is 150 GiB (`WORKER_DISK_GIB` in the local env file), applied at the next render and head restart. Throughput can be raised later if large pulls prove slow.
- The head's 20 unneeded images (196 GB) are **not** being deleted (decided: skip); the head has 289 GB free. Risk noted: a full head disk takes Postgres down, so a disk guard is part of the run.

## 3. Design: token relay (temporary)
| Piece | Behaviour |
|---|---|
| Mac refresher (`push_vertex_token.py`, built) | every 30 minutes by default: fetch a one-hour access token, write it atomically to the head through ssh's standard input with retries; loud on failure; keeps the Mac awake with `caffeinate` (a closed lid still sleeps the Mac); deletes the file on exit |
| Head shim | started from the registry reference with the token file; temporary change: re-read the file when it changes; on a 401 or 403 re-read and retry once |
| Token relay (head) | about 40 lines, standard library; serves the current token over the private network to callers presenting the shim master key; bound to the head's private address; never logs the token |
| Worker shim | temporary change: key source is a URL; fetch at start (fail fast), refetch every few minutes, refetch and retry once on 401 |
| Retries | a larger 429 retry budget with jitter (configurable) |
| Security | one-hour tokens only; the login file never leaves the Mac; the relay port is reachable between nodes with no change: the head and the workers share the cluster security group, which allows all traffic from members of itself (checked 2026-11-03); all of it removed when the service account or federation arrives |

The exact address and auth settings for our head (port 6381, client port 9991) are not recorded in our notes: confirm in a dry run.
5. **Worker tests:** one worker on a Bedrock model (no token; proves the worker starts a shim from a reference), then Vertex through the relay.
6. **Staged ramp on dev tasks: ranks 101 to 120 of the same random order** (outside the 100, so scored tasks are not contaminated), e2e: 1 task through the autoscaler, then 8, then 20 with scale-up to 2 workers. This spans several token rotations and is where the 10-slot setting is checked: CPU pressure on each node, how much grading rebuilds stretch, tasks hitting the 90-minute limit because of load. Watch: 429s, context errors, disk, Postgres connections (about 2 per task; default limit 100), skipped artifacts (the cap is 25 MB per file; a skipped file is lost when a worker is terminated), cost, the quality of long DeepSeek sessions through the chat adapter (the smoke test was 3 minutes).
7. **Gates for the 100:** the Vertex quota (ask the owner), a long-prompt probe of the context limit, the price (or accept token caps with cost shown as 0), measured image sizes and pull times from stage 6, the DeepSeek protocol variant written, the validity screens run on the 100 ([[wiki/syntheses/qwen-100-task-study-protocol]] section 4).
8. **Run the 100:** `max_workers` 2 (head plus 2 workers, 48 vCPUs, 30 slots), a kill switch (`stop_workers.sh`), a watcher on the instance count, a disk guard (stop launching above about 85% use), a check that the refresher is alive, `run --resume` to continue after any interruption.
9. **Wrap-up:** Postgres backup copied to the Mac, token files deleted, workers terminated, instance stopped, results and costs written up.

## 5. Estimates and risks
- **Time:** DeepSeek's earlier e2e runs had a median of about 16 minutes and about $0.06 each (valid runs on the five tasks, OpenRouter prices); 100 tasks at 30 slots is plausibly 2 to 3 hours including tails, not the 15 hours of a 90-minute worst case.
- **Cost:** Vertex price unknown; at the earlier prices about $10 to $20 for 100 runs, to be confirmed.
- **Risks:** runaway worker launches (mitigation: `max_workers` 2, the one-worker test first, the watcher); the Mac or login dropping mid-run (nodes get 401s, tasks in flight fail as infrastructure errors, passed tasks are kept; Google's default session limit can force a re-login after about 16 hours); Vertex quota or rate limits at 30 concurrent agents; CPU overload at 10 e2e slots per node; image pull time and Docker Hub limits; the head's flaky SSH (stalled twice in one day).

### Disk decision (2026-11-03)
Neither CyberGym nor the runner removes task images (containers are removed with `docker run --rm` and `cleanup_container`; no `rmi`, no prune anywhere), so each node keeps the image of every task it runs. Decision: worker disks 1024 GiB (`WORKER_DISK_GIB=1024` in the VM's `autoscaler.local.env`, cluster file re-rendered; the only change in the prepared file is `VolumeSize`; backups `*.pre-disk1024`) and the head's images the 100 do not use were removed (29 of 41 images; head disk 279 GB to 41 GB used). No cleanup job for now. The image prefetch line stays out of the VM's template until it has a window (unwindowed it would fill each worker to the 150 GB floor); the running autoscaler's reload of the new size is confirmed only when the first worker's `df` shows about 1 TB.

### Caps decision: $10 per run plus 90 minutes (2026-11-03)
This is a replication of the CyberGym paper, so the only limits are the paper's: 10 USD per run and 90 minutes. The study owner set the price to assume: 0.30 USD per million fresh input tokens, 0.03 cached, 1.20 output (aggregator listings of the Vertex rate; not yet checked on Google's own page, which could not be read). The registry entry `deepseek-v4.1-flash@vertex` now carries the price, so token-only mode no longer starts for it (a priced remote model needs a per-key dollar cap). Worker caps are `WORKER_SHIM_CAPS=1000` (a 1000 USD safety total per node, the default 10 USD per key). The head shim was restarted in this mode (health: 10 per key, 1000 total); one call cost 0.0000057 USD, matching the arithmetic. From the token counts of the 10 stage-2 tasks, per-task cost at these prices was about 1.64 USD on average and 7.05 at most (so the cap would not have cut any of them); the 100 would then cost roughly 160 USD (an extrapolation).
