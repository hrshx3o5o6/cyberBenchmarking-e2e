# 30-task test of the full path: autoscaler + shared Postgres (living page)

Part of [[wiki/syntheses/ray-autoscaler-build-plan]] and [[wiki/syntheses/shared-postgres-state-design]]. **Status: first run finished (19 passed, 11 infra_error: 10 race failures + 1 task stopped by the operator); fix deployed; terminate-on-idle switched on; re-run of the 10 on hold pending the owner's OK for a larger run; updated phase by phase below.** Goal: see how 30 never-tried tasks are split between the head and an autoscaled worker, how many workers start, what the model calls cost, and whether **everything a worker produced is in Postgres** (the condition for terminating workers later).

## 1. Plan
| Item | Setting |
|---|---|
| Tasks | 30 light patch-only tasks (base image only), seeded random pick (seed 20261030), one task per project (30 projects), **never used before on the VM** (checked against every manifest, state file and run log; none appear in this wiki) and with data present on the Hugging Face dataset (313 of 318 candidates had it) |
| Model / agent | Kimi K3 on Bedrock through Codex (same as the earlier runs) |
| Head | the existing 16-vCPU VM, 10 slots, our autoscaling Ray head (port 6381) restarted with the `.env` loaded (shim key and database URL in its Ray environment) |
| Workers | `m7i.4xlarge` (same type as the head), 10 slots, `max_workers` 3; **the vCPU quota (reported as 40, unverified) lets only one fit** next to the head (16 + 16 = 32; a second would need 48), so extra launches are expected to be rejected with `VcpuLimitExceeded` (harmless, logged) |
| Postgres | hosted on the head VM; the driver registers all 30 executions, each task mirrors state, result and artifacts and reads them back before it returns |
| Stop vs terminate | workers **stay stopped** (`cache_stopped_nodes` true) until `sync-check` passes everywhere |
| Spend (estimates) | expected about $16 (24 earlier Kimi K3 patch-only runs: mean $0.53, median $0.36, p90 $0.70, max $2.85), about $21 if every task cost the p90; per-node shim caps: head $15 total (about $2.29 already spent), worker $10, so the ceiling with the quota as it is is about $23; plus about $0.4 for the worker |
| Expected time | 20 slots at once, then 10 more: about two waves of about 7 minutes (earlier mean; p90 9, max 15) plus a few minutes for the worker to boot, fetch data and start its shim |

## 2. Safeguards
Monitoring about every 30 to 40 seconds (nodes and slots, EC2 states and vCPUs in use, each node's load and CPU pressure, shim spend per node, tasks per host and status from Postgres); stop conditions: a second worker or more than the quota's vCPUs, a node unreachable, the head VM's load too high for a shared machine, a node near its spend cap, or a cluster of failures. The owner's Ray head (port 6379) and our old head (6380) are never touched; processes are stopped only by exact PID.

- **Finding 1, a latent runner bug (not caused by Postgres): 10 of 30 tasks (6 on one worker, 4 on the other) ended as `infra_error` within seconds of the workers joining**, with `sqlite3.OperationalError` at `PRAGMA journal_mode=WAL` in `db.connect`. The head did not hit it because the driver had already created its state file. It only shows on a fresh node with concurrent tasks. The tasks never started (no hostname, no model spend), and the **dead-task handling worked as designed**: the driver recorded them as `infra_error` with the full error text in Postgres and carried on instead of crashing. (Correction: an earlier version of this page said 5 on each worker.) Plan: after this run, make `db.connect` retry briefly (and/or create the file under the stagger lock), then re-run these 10 with `run --resume`.

- **Why the split was uneven, and the terminate question** are answered in the discussion below this entry's date in the log; the short version: the scheduler dispatched evenly (10 per node); the unevenness came from the failures; and termination after logging is supported by the per-task read-back evidence, to be switched on after one more verification.
- **Automatic termination of idle workers (requested, 2026-10-30): prepared, not yet switched on.** The cluster template now takes `cache_stopped_nodes` as a parameter (`false` = the autoscaler terminates an idle worker and deletes its disk; `true` = it stops it), with a short idle window (3 minutes, so a worker goes shortly after its last task but a final check is still possible). Why it is safe here: every finished task has already read its own upload back from Postgres (`observations_synced: true` on all 20 results that reached the sink), so a node holds nothing that is not in Postgres once its tasks have returned, and verification after the fact needs only Postgres, not the node. Limits: a task that dies mid-way loses its partial data (re-runnable); node-level metrics are not streamed yet; a node cannot be inspected after it is gone, so any node-local `sync-check` must run inside the idle window; the autoscaler reads `cache_stopped_nodes` only when it starts, so switching it needs a head restart; reused stopped nodes do not get new code (the autoscaler skips the file sync when its runtime hash is unchanged), which is one more reason to terminate rather than stop.
